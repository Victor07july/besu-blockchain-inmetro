# Implementação 2: Monetização E1 com GPS e Privacidade Diferencial

## Teoria

A fórmula E1 monetiza a redução de emissões de CO2 comparando o comportamento real de veículos flex com uma meta calculada baseada nas especificações do fabricante. O problema central é que os dados de geolocalização GPS, necessários para validar as distâncias percorridas e detectar fraudes, expõem informações sensíveis sobre os deslocamentos dos usuários, violando sua privacidade. A Privacidade Diferencial (DP) resolve esse problema adicionando ruído calibrado às coordenadas GPS antes de enviá-las à blockchain, garantindo que seja matematicamente impossível reconstruir a trajetória exata do veículo a partir dos dados publicados.

O mecanismo de Laplace adiciona ruído aleatório às coordenadas de latitude e longitude com distribuição proporcional ao parâmetro epsilon (ε). Um epsilon baixo (por exemplo, 0.1) fornece forte privacidade mas adiciona muito ruído (até centenas de quilômetros), enquanto epsilon alto (por exemplo, 10.0) preserva mais a utilidade dos dados mas oferece menos proteção. O ruído segue a distribuição Laplace(0, 1/ε), onde a sensibilidade é 1.0 grau de coordenada. Na prática, com ε=1.0, o erro médio fica em torno de 100-170 km, o que distorce significativamente as posições mas ainda preserva parcialmente as relações de distância para a monetização.

Além do GPS com DP, a implementação usa pseudônimos HD (Hierarchical Deterministic) gerados deterministicamente a partir de um seed BIP-44. Cada viagem recebe um endereço único derivado do caminho BIP-44 `m/44'/60'/0'/0/{index}`, onde `m` é a raiz da carteira (master seed gerada da frase mnemônica), `44'` é o padrão BIP-44 (apóstrofo indica derivação "hardened"), `60'` é o código para Ethereum, `0'` é a conta 0, `0` é a external chain (endereços de recebimento), e `{index}` é o índice incremental (0, 1, 2...) que gera endereços diferentes para cada viagem. Partindo de uma única frase mnemônica, é possível gerar infinitos endereços sem conexão aparente, desvinculando as transações da identidade real do proprietário do veículo. Isso impede que um observador da blockchain conecte múltiplas viagens ao mesmo usuário apenas pelos endereços, complementando a proteção geográfica do DP. O contrato armazena os dados privados na blockchain Hyperledger Besu (QBFT) e calcula a distância GPS usando uma aproximação simplificada da fórmula de Haversine, determinando o valor E1 a pagar ou penalizar baseado na diferença entre emissão real e meta.

## Prática

O contrato `E1RegistryGPS.sol` define a estrutura `TripGPSParams` que encapsula todos os dados de uma viagem: VIN do veículo, timestamp, distâncias de rodovia e cidade, porcentagem de etanol, consumos do fabricante, emissão real, preço do carbono, pseudônimo HD e coordenadas GPS de início e fim. As coordenadas são armazenadas como `GPSLocation(int256 lat, int256 lon)` multiplicadas por 1e6 para preservar 6 casas decimais sem usar ponto flutuante. A função `registerTrip()` recebe esses parâmetros, calcula a distância GPS usando `_calculateGPSDistance()`, compara com a meta de CO2 calculada pela fórmula E1, e determina o valor monetário (positivo para recompensa, negativo para penalidade). O contrato foi compilado com Solidity 0.8.19 usando o modo via-IR para resolver o erro "Stack too deep" causado pelo grande número de variáveis locais.

O deploy foi implementado em `deploy_e1_gps.py` usando `py-solc-x` com compilação via `compile_standard()` e flag `viaIR: true`. A conexão com o Besu teve que contornar a limitação do método `is_connected()` que falha com erro 401 ao tentar chamar `net_version` ou `web3_clientVersion`. A solução foi injetar o middleware `ExtraDataToPOAMiddleware` antes de qualquer chamada e usar métodos `eth_chain_id` e `eth_block_number` para validar a conexão, pois esses não requerem autenticação adicional. O deploy gera o arquivo `e1_gps_contract_address.json` contendo endereço, ABI e RPC URL para uso pelos scripts de interação.

O script `send_e1_gps_data.py` carrega o CSV com os dados das viagens, parseia as coordenadas GPS do formato string, aplica o ruído Laplace às coordenadas usando `add_laplace_noise()` com epsilon configurável, e envia cada viagem para o contrato. Os pseudônimos HD são gerados on-the-fly usando `Account.from_mnemonic()` com paths incrementais. O script `compare_dp_nodp.py` automatiza a comparação enviando as mesmas 33 viagens duas vezes: primeiro com DP aplicado (epsilon=1.0) e depois com coordenadas originais, usando paths HD diferentes (offset +1000 para no-DP) para distinguir os dois conjuntos. O script gera o CSV `comparison_dp_vs_nodp.csv` com todas as métricas lado a lado: coordenadas originais, coordenadas usadas, erro GPS em km, distância calculada pelo contrato, valores E1, e hashes das transações, permitindo análise estatística e visualização gráfica do trade-off entre privacidade e utilidade dos dados.
